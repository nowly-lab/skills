# Release after merging main

For the products in the `orca-push-all-main` allowlist (see that skill for where the list is configured), the user's standing release policy treats an authorized merge to `main` as authorization to release that merged revision to every existing, verified, product-owned production surface. Do not ask again for routine deployment approval. An explicit instruction to stop, wait for review, avoid deployment, or use a narrower scope takes precedence. Invoking a skill or opening a PR alone does not authorize merging.

Before merging, complete relevant local tests, independent review (or an owner-recorded substitute reviewer when the intended reviewer is unavailable), fixes and re-review, and relevant QA. Respect repository branch protections and actual platform approval requirements. Verify repository identity, the exact origin push destination, and the outgoing revision. Do not force push, change remotes, or include unrelated outgoing commits. Never infer successful verification from a failed command.

Use the product's implementation/release skill (its own tips skill, or `AGENTS.md`/`CLAUDE.md`, if present), package commands and owned provider configuration as the release inventory. Keep `AGENTS.md` limited to architecture, code/security constraints, command references and short skill links; implementation coordination and release procedures belong in skills. Inspect all existing Web, backend, desktop, iOS, and extension surfaces as applicable. Recheck service ownership, environment, credentials, signing identity, distribution destination, and production data boundaries before any effect. Keep secret values out of files, arguments, logs, and evidence. Release authorization includes provisioning product-owned infrastructure and least-privilege credentials needed for that release, after verifying account ownership and protected credential storage. It does not authorize destructive data changes, unrelated live dispatch, or bypassing a platform approval.

Build, package, install, deploy, and distribute are separate outcomes. Execute each existing surface's actual release procedure. Then read back the deployed artifact or version and verify the relevant public flow against the merged revision. A dry run, successful build, local preview, or uploaded but unpublished store submission does not establish production release. If the exact required artifact is already deployed and verified, retain that evidence and avoid redeploying it unnecessarily.

Record each surface's command, main SHA, artifact version or digest, actual destination, release result, and verification evidence. Missing credentials, OS consent, signing profiles, provider access, or an established target make that surface incomplete until resolved within the authorized scope. State the exact blocker and continue independent surfaces. Do not invent a target or mark the overall release successful while a required surface remains incomplete. Preserve evidence before removing a clean, completed, owned worktree.

When the product is the host that runs the agents themselves (for example a build of Orca), confirm with the user before restarting it, because other sessions may be active. An installed app belongs exclusively to its own verified product release; never overwrite another product's installed app. Each product keeps its distinct app, extension, storage, and session identities.

The push-only command retains its no-commit and no-branch-switch behavior. Only an explicit implementation and release task authorizes creating commits, PRs, and normal merges within its assigned scope. The allowlist, repository identity checks, exact destination checks, data protection, and secret protections still apply.
